AIDC / Chthonia Platform

From prototype to a deliverable, governable, and observable AI Data Center control plane
← Back to English Resume | 中文

The purpose of this project is to build an internal AI Data Center control plane, so GPU, Container, and Bare-metal compute resources can be requested, allocated, deployed, monitored, and governed instead of remaining as data center equipment and manual operations.

Kubernetes / MicroK8s Helm / Argo CD IDC / Cluster / Container IAM / API Gateway Monitoring / Reliability

What This Project Is For

Compute Resource Entry Point

Turns GPU, IDC, Cluster, Container, Quota, User, and Project into resources that can be managed and requested through the portal.

Platform Service Control Plane

Supports Admin Console / Service Portal so admins and users can operate resources, read status, and enter services.

Delivery And Environment Governance

Allows platform services to be deployed and verified across Lab, AWS, and MicroK8s environments through Helm, image versions, and Argo CD.

Reliability And Observability

Connects monitoring, UAT, HA, VM recovery, GPU tests, and incident handling so the platform can be operated instead of only demoed.

What The Platform Solves

  • Turns GPU, IDC, Cluster, Container, Quota, User, and Project into manageable resources.
  • Separates CPU service clusters from GPU workload clusters so platform services and AI compute resources do not interfere with each other.
  • Enables Admin Console governance for organizations, projects, members, IDC, Cluster, Quota, and system settings.
  • Enables Service Portal access to Project, Quota, Container, resource status, and service entry points.
  • Keeps a manual deployment control point for shared GPU test environments to reduce wrong-version and accidental deployment risk.

Service Cluster And GPU Cluster Split

CPU Service Cluster

Portal, IAM / SSO, API Gateway, database, and monitoring services do not directly use GPUs, so they run on a CPU cluster. This separates the platform control plane from compute workloads.

GPU Workload Cluster

GPU resources are managed by another cluster. If an environment has 8 GPU cards, kubectl get nodes can show 8 GPU nodes; when a customer requests 2 GPUs, the platform allocates the corresponding 2 nodes as that customer's workload cluster.

IAM / SSO Integration

Authentication And Permission Flow

Helped integrate Keycloak as the SSO service for login, permission control, session handling, and portal user / project permissions. Also helped evaluate public Keycloak email limitations and support customized email invitation flow across frontend and Go server work.

White-label Styling And Deployment

Supported frontend changes to Keycloak login / redirect styling to reduce the sense of leaving the product. Packaged the modified theme / realm config as a Docker image so IAM could be deployed consistently across environments.

Delivery Flow

Code To Image

The portal repo owns application code and image output. After feat/* is merged into dev, CI builds a versioned image and pushes it to GHCR as the deployment source for Lab / AWS environments.

Image To Environment

The portal-helm repo manages Helm charts and deployment settings. dev maps to Lab and qas maps to AWS. Because the Lab test environment is shared, Argo CD uses manual version selection and sync to avoid impacting shared resources.

Monitoring Case: Argo CD Noise After Lab Power Outage

Problem

After an unexpected Lab power outage, the MicroK8s cluster could enter an abnormal state and Argo CD would continue sending invalid API requests, creating noisy logs and alerts.

Handling

After analyzing cluster state and log behavior, clarified a shutdown procedure: during predictable maintenance, stop worker nodes first and then stop the control node.

Result

Wrote a daily log check script to track abnormal requests and handed the logic to the monitoring team, which later turned it into a built-in product module.

Reliability And Validation

  • End-to-End UAT: verified that Admin Console and Service Portal major flows could run through.
  • Cluster HA / VM Recovery: verified service recovery after node and VM failures.
  • Data Integrity: verified that platform state and data could continue across abnormal scenarios.
  • NCCL / RDMA GPU Test: verified GPU communication ability under AI workloads.
