SRBG Data Platform and Workflow Management System

From scattered VM Cronjobs to a governable ETL Job Management Console
← Back to English Resume | 中文

The purpose of this project is to turn data workflows scattered across VM Cronjobs, DB tables, logs, and product lines into an ETL Job Management Console that can monitor jobs, restart failures, trace dependencies, and track cost.

ETL Job Management Dependency Visualization Restart / Step Restart ADF / K8s Pod Cost Analysis

What This Project Is For

Scheduling Governance Entry Point

Centralizes job status, execution history, and data source information that used to be scattered across VMs, DB tables, logs, and projects.

Failure Handling Flow

Allows failed jobs to be handled through failed restart, step restart, and project restart flows instead of relying fully on manual judgment.

Dependency And Data Flow

Platformizes parent-child dependency, loop check, and downstream impact so failure sources and impact scope can be located faster.

Runtime Architecture Transition

Gradually moves convertible batch jobs toward ADF / K8s Pod without interrupting existing schedules, reducing long-term VM Cronjob pressure.

What Jay Yu Changed

From "query data" to "read the platform"

BeforeJob status was scattered across VMs, DB tables, logs, and different projects, so incidents first required finding where a task had stopped.

AfterRD / PM teams could see batch status, execution history, data sources, and recent failure points from the Console, shifting discussion from where to check to how to handle the issue.

From manual reruns to a standard flow

BeforeAfter a job failed, RD needed to decide which step to rerun and which downstream tasks would be affected; handling varied by person.

Afterfailed restart, step restart, and project-level restart were organized into a consistent flow, reducing manual judgment and cross-team confirmation cost.

From human memory to platform tracking

BeforeScheduling relationships depended on documents, experience, or manual questions; downstream impact was hard to confirm quickly when an upstream task failed.

Afterparent-child dependency tree, loop check, and downstream impact entered the platform, making failure sources and impact scope directly traceable.

From feature accumulation to a deliverable platform

BeforeAs platform features expanded, quality checks, deployment workflow, and resource configuration needed a more stable engineering foundation.

AfterCI/CD, SonarQube, unit testing, and Terraform became part of delivery, allowing the platform to keep evolving instead of being a one-off feature set.

State Before The Change

  • Jobs were scattered across VMs, DB tables, logs, and projects, without one entry point for the overall view.
  • When an upstream job failed, downstream impact needed experience and manual investigation to judge.
  • Failure restart, step rerun, and project-level restart lacked a consistent operation flow.
  • Some jobs still ran on legacy VM / Cronjob architecture every day, so migration could not interrupt the existing schedule.
  • Cost, events, data sources, and job history were fragmented, increasing confirmation cost between RD and users.

Engineering Work Behind The Change

Batch Setting / Job Console

Worked on master / detail APIs, schedule creation and editing, DTO validation, status query, execution history, and data source tracing.

Dependency & Restart

Worked on dependency tree, loop check, failed restart, step restart, and project-specific restart flows.

ADF / Pod / VM Transition

Helped move convertible batch jobs toward ADF / K8s Pod while preserving management and traceability for existing VM jobs.

Quality / Delivery

Introduced CI/CD, SonarQube, unit testing, and Terraform so platform features could be tested, deployed, and tracked.
