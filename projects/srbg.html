SRBG 資料平台與排程管理系統

從分散 VM Cronjob 到可治理的 ETL Job Management Console
← 回到履歷｜English

這個專案的目的，是把事業群內分散在 VM Cronjob、DB、Log 與各產品線中的資料排程，整理成可監控、可重啟、可追蹤相依與成本的 ETL Job Management Console。

ETL Job Management Dependency Visualization Restart / Step Restart ADF / K8s Pod Cost Analysis

這個專案在做什麼

排程治理入口

把原本散在 VM、DB、Log 與各專案裡的排程狀態、執行紀錄與資料來源，集中到一個 Console。

失敗處理流程

讓排程失敗後可以依照 failed restart、step restart、project restart 等流程處理，而不是完全依賴人工判斷。

相依與資料流

把 parent-child dependency、loop check 與 downstream impact 平台化，讓異常來源與影響範圍更容易被定位。

執行架構轉換

在不中斷既有排程的前提下，逐步把可轉換批次任務導向 ADF / K8s Pod，降低長期 VM Cronjob 維運壓力。

Jay Yu 改變了什麼

從「查資料」變成「看平台」

原本排程狀態散在 VM、DB、Log 與不同專案中，問題發生時要先花時間查任務跑到哪裡。

改變RD / PM 可以從 Console 看到 batch 狀態、執行紀錄、資料來源與最近失敗點，討論焦點從「去哪查」變成「怎麼處理」。

從「人工重跑」變成「標準流程」

原本任務失敗後，要靠 RD 判斷該重跑哪個步驟、哪些下游會受影響，處理方式容易因人而異。

改變failed restart、step restart 與指定專案重啟被整理成一致操作流程，降低手動判斷與跨團隊確認成本。

從「人腦記相依」變成「平台追蹤」

原本排程前後關係依賴文件、經驗或人工詢問；前置任務失敗時，下游影響範圍不容易快速確認。

改變parent-child dependency tree、loop check 與 downstream impact 進入平台，異常來源與影響範圍可以被直接追蹤。

從「功能堆疊」變成「可交付平台」

原本平台功能持續擴張，但品質檢查、部署流程與資源配置需要更穩定的工程基礎支撐。

改變CI/CD、SonarQube、單元測試與 Terraform 進入交付流程，讓平台能持續演進而不是只交付一次性功能。

可被驗證的改變

22 內部專案使用或被平台支援
100+ 使用者與多個 RD / PM 團隊
3 主要專案批次任務導入 ADF / K8s Pod
CI/CD SonarQube、單元測試與 Terraform 導入

改變前的狀態

  • 排程散在 VM、DB、Log 與各專案中，沒有單一入口能快速看全貌。
  • 前置排程失敗時，下游影響範圍需要靠經驗與人工查詢判斷。
  • 失敗重啟、指定步驟重跑、專案層級重啟缺乏一致操作流程。
  • 部分任務仍在舊 VM / Cronjob 架構中，每天都在跑，不能用中斷式改造。
  • 成本、事件、資料來源與排程歷程分散，RD 與使用者確認問題的成本偏高。

支撐這些改變的工程工作

Batch Setting / Job Console

參與 master / detail API、排程新增與編輯、DTO 檢核、狀態查詢、執行紀錄與資料來源追蹤。

Dependency & Restart

參與 dependency tree、loop check、failed restart、step restart 與指定專案重啟流程。

ADF / Pod / VM 轉換

協助可轉換的批次任務移往 ADF / K8s Pod，同時保留既有 VM 任務的管理與追蹤能力。

Quality / Delivery

導入 CI/CD、SonarQube、單元測試與 Terraform，讓平台功能可被測試、部署與追蹤。

產出與影響

  • 排程問題從「散在各處查」變成「從平台入口追蹤」。
  • 失敗處理從「RD 人工判斷」變成「可重啟、可追蹤的一致流程」。
  • 相依關係從「靠文件與經驗」變成「平台可視覺化」。
  • 可轉換批次任務從 VM Cronjob 逐步遷移至 ADF / K8s Pod，降低長期維運壓力。
