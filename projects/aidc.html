這個專案的目的，是建立企業內部 AI Data Center 控制面，讓 GPU、Container、Bare-metal 等算力資源可以被申請、分配、部署、監控與治理，而不是停留在機房設備與人工維運流程。

Kubernetes / MicroK8s Helm / Argo CD IDC / Cluster / Container IAM / API Gateway Monitoring / Reliability

算力資源入口

平台服務控制面

支援 Admin Console / Service Portal，讓管理者與使用者能操作資源、查看狀態、進入服務。

交付與環境治理

讓平台服務可以透過 Helm、image 版本與 Argo CD 在 Lab / AWS / MicroK8s 等環境被部署與驗證。

可靠性與觀測

整合監控、UAT、HA、VM recovery、GPU test 與異常處理流程，讓平台能被維運而不只是 Demo。

平台在解什麼問題

  • 區分 CPU service cluster 與 GPU workload cluster，避免平台服務與 AI 算力資源互相干擾。

  • 讓共享 GPU 測試環境保留人工部署控制點，降低錯版與誤部署風險。

Service Cluster 與 GPU Cluster 分工

CPU Service Cluster

Portal、IAM / SSO、API Gateway、資料庫、監控等平台服務本身不直接使用 GPU，因此放在 CPU cluster，讓平台控制面與算力工作負載分離。

GPU Workload Cluster

GPU 資源由另一個 cluster 管理。若環境有 8 張 GPU card，在 kubectl get nodes 可視為 8 個 GPU nodes；當客戶 request 2 張 GPU，平台會將對應 2 個 nodes 組成該客戶可使用的 workload cluster。

IAM / SSO 整合

認證與權限流程

協助整合 Keycloak 作為 SSO 認證服務，處理登入、權限控管、session 與 Portal 使用者 / 專案權限管理；也協助評估 Keycloak 公版信件限制，支援前端與 Go server 端的 email invitation 客製化流程。

白牌化與部署

協助前端調整 Keycloak login / redirect UI 樣式，降低使用者察覺第三方認證頁面的斷裂感；將修改後的 theme / realm config 打包成 Docker image，讓 IAM 服務可隨環境一致部署。

Image 到環境

portal-helm repo 管理 Helm chart 與部署設定；dev 對應 Lab 環境、qas 對應 AWS 環境。由於 Lab 測試環境仍有其他人共用，Argo CD 採手動選版與同步，避免自動部署影響共享資源。

監控案例：Lab 斷電後的 Argo CD 噪音

問題

Lab 環境非預期斷電後，MicroK8s cluster 可能進入異常狀態，Argo CD 持續送出無效 API request，讓 log 與告警變得很吵。

處理

分析 cluster 狀態與 log 行為後，整理 shutdown procedure：可預期維護時先停 worker nodes，再停 control node。

結果

撰寫每日 log 檢查 script 追蹤異常 request，並把檢查邏輯交給 monitoring 團隊，後續轉成產品內建模組。

可靠性與驗證

  • End-to-End UAT：確認 Admin Console 與 Service Portal 主要流程可完整串起。
  • Cluster HA / VM Recovery：驗證節點與 VM 異常後的服務恢復能力。
  • Data Integrity：確認平台狀態與資料在異常情境下仍可延續。
  • NCCL / RDMA GPU Test：確認 AI 工作負載下的 GPU 通訊能力。
